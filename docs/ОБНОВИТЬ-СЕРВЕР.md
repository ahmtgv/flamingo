# Обновить сервер занятий · рецепт

Этот лист — про **обновление** уже стоящего сервера `api.flamingo.plus`.
Установка с нуля описана отдельно, в `ЧТО-ДЕЛАТЬ-01.09.md`, и повторять её не надо.

| Что | Где |
|---|---|
| сервер | `root@82.147.71.204` |
| код | `/opt/flamingo-v2`, ветка `v1` |
| служба | `flamingo` (systemd, gunicorn на `127.0.0.1:8000`) |
| база | `/var/lib/flamingo/flamingo.sqlite3` |
| пособия | `/var/lib/flamingo/materials/` |
| снаружи | Caddy в docker → `api.flamingo.plus` |

⚠️ **Пуш в `v1` обновляет только сайт.** Cloudflare собирает фронт, сервера он не
касается вовсе. Каждый коммит в `backend/` живёт в репозитории до тех пор, пока
кто-то не выполнит этот лист руками.

## 🔴 Ловушка: старый рецепт из трёх строк ломает боевое

В `ЧТО-ДЕЛАТЬ-01.09.md` (шаг 12д) записано обновление в три строки:

```
cd /opt/flamingo-v2 && git pull
systemctl restart flamingo
```

Оно верно ровно до тех пор, пока в коммитах нет **миграций** — инструкций,
заводящих в базе новые столбцы. Как только они появились, этих строк мало:
код приезжает новый, база остаётся старая, и сервер умирает на первом же запросе.

Померено 08.09 на копии боевой базы: база с миграциями до `0002`, код с `0003`.

```
Person.objects.first()      → OperationalError: no such column: people.tz
Lesson.objects.all()[:1]    → OperationalError: no such column: lessons.tz
```

`Person.objects.first()` — это «кто вошёл», он выполняется **на каждый запрос**.
То есть падает не журнал и не расписание, а всё сразу: вход, кабинет, журнал,
комната. Сайт при этом жив и выглядит целым — молчит только сервер.

**Правило.** Перед обновлением всегда смотреть, есть ли новые миграции:

```
cd /opt/flamingo-v2 && git fetch
git diff --name-only HEAD origin/v1 -- 'backend/*/migrations/*'
```

Пусто — хватит трёх строк. Не пусто — весь лист ниже.

🔴 **Звёздочка в конце обязательна, и кавычки тоже.** Первая редакция этой строки
кончалась на `backend/*/migrations/` — и на коммитах, где обе миграции лежат прямо
там, находила **ноль файлов**. Проверено 08.09 четырьмя вариантами подряд:

```
backend/*/migrations/     → 0     ❌ так было написано
backend/*/migrations/*    → 2     ✅
*/migrations/*            → 2
backend/**/migrations/**  → 2
```

Проверка, которая молчит на настоящем расхождении, хуже отсутствующей: она
разрешает идти дальше. Именно этот ноль сказал бы «миграций нет, хватит трёх
строк» — и уронил бы боевое.

## Порядок и почему именно такой

```
1. копия базы      ← единственное, что нельзя пересоздать
2. git pull        ← работающая служба этого не замечает: код у неё уже в памяти
3. pip install     ← зависимости; тоже мимо работающей службы
4. migrate         ← новые столбцы. Старый код в памяти их просто не видит
5. restart         ← и только теперь новый код встречает новую базу
```

Между шагами 2 и 5 сайт работает как работал. Если переставить `restart` перед
`migrate` — получится ровно та поломка, что описана выше, и продлится она столько,
сколько занимает набрать следующую команду.

## Шаги

**0. Копия базы и пособий.** Тридцать секунд, и они окупаются один раз в жизни.

```
ssh root@82.147.71.204
sqlite3 /var/lib/flamingo/flamingo.sqlite3 ".backup '/var/backups/flamingo-до-$(date +%F-%H%M).sqlite3'"
tar czf /var/backups/materials-до-$(date +%F-%H%M).tgz -C /var/lib/flamingo materials
ls -la /var/backups | tail -4
```

**1. Забрать код.**

```
cd /opt/flamingo-v2
git pull
git log --oneline -1
```

Верхний коммит должен совпасть с тем, что в репозитории на маке.

**2. Зависимости.**

```
cd /opt/flamingo-v2/backend
.venv/bin/pip install -r requirements.txt
```

🔴 Пропустить нельзя, даже если «ничего не менялось»: `common/пояс.py` нарочно
падает при запуске, если базы часовых поясов нет вовсе. Лучше громко при старте,
чем тихо отвергать каждый пояс как незнакомый.

**3. Миграции.**

```
.venv/bin/python manage.py migrate
```

Каждая строка должна кончаться `OK`. Ошибка здесь — **остановиться и не
перезапускать службу**: старый код в памяти всё ещё обслуживает людей.

**4. Прибор.** Он гоняет живой Django на отдельной базе в `/tmp`, боевую не трогает.

```
.venv/bin/python study/прогон.py
```

Ждём `✅ всё сходится`. Не сошлось — не перезапускаем.

**5. Перезапуск.**

```
systemctl restart flamingo
systemctl status flamingo --no-pager | head -5
```

## Проверка — с самого сервера, потом снаружи

```
curl -s http://127.0.0.1:8000/api/auth/me
curl -s https://api.flamingo.plus/api/room/healthz
```

Ждём `{"person": null}`. Пришла HTML-страница — служба не поднялась, смотреть
`journalctl -u flamingo -n 50`.

🔴 **А вот `livekit` здесь отвечает `false`, и это НЕ поломка обновления.**
Проверено 08.09 сразу после первого прохода по этому листу. Разбор:

| Кто отвечает | `/api/room/healthz` | Кто им пользуется |
|---|---|---|
| функция Cloudflare Pages, `flamingo.plus` | `{"ok":true,"livekit":true}` | **весь продукт**: `src/lib/api.ts` на боевом ходит СВОИМ адресом, не в `api.` |
| Django, `api.flamingo.plus` | `{"ok":true,"livekit":false}` | никто |

То есть подпись пропуска в комнату на боевом делает функция Pages, а у Django
ключей LiveKit просто нет, и он про это честно говорит.

⚠️ **Но мёртвой эту половину называть рано, и в этом мина.** `common/livekit.py`
без ключей подписывает токен запасным путём — SECRET_KEY Django. Облако такой
токен отклоняет. Значит путь достижим и выдаёт пропуска, которые никто не
примет, молча. Пока обе реализации живы, три строки `LIVEKIT_*` должны стоять и
в `.env` сервера — те же значения, что в переменных проекта Pages.

Проверить, не показывая значений:

```
cd /opt/flamingo-v2/backend
for k in LIVEKIT_URL LIVEKIT_API_KEY LIVEKIT_API_SECRET; do
  grep -q "^$k=.\+" .env && echo "$k: задан" || echo "$k: пусто"
done
```

Отдельно и не сегодня: одна вещь продукта — пропуск в комнату — сделана дважды.
Решать, какая из двух остаётся, владельцу. Довод за Django: он знает, КТО вправе
войти в комнату; функция Pages выдаёт пропуск любому, кто знает код.

Дальше — из браузера, где вы вошли. В консоли на flamingo.plus:

```
fetch('https://api.flamingo.plus/api/study/lessons?month=2026-09',{credentials:'include'})
  .then(r=>r.json()).then(j=>console.log('пояс приехал:', 'пояс' in j.уроки[0]))
```

`true` — сервер догнал репозиторий. `false` — обновление не доехало.

## Откат

Код:

```
cd /opt/flamingo-v2 && git log --oneline -5
git checkout <прежний коммит>
systemctl restart flamingo
```

База — только из копии шага 0:

```
systemctl stop flamingo
cp /var/backups/flamingo-до-<метка>.sqlite3 /var/lib/flamingo/flamingo.sqlite3
chown www-data:www-data /var/lib/flamingo/flamingo.sqlite3
systemctl start flamingo
```

⚠️ Откат базы стирает всё, что люди сделали после копии. Это последнее средство,
а не способ «попробовать ещё раз».
