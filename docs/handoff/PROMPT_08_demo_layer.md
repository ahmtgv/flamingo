## Контекст и цель
flamingo.plus сейчас отдаёт наш фронт (дизайн AIR), но бэкенда НЕТ. В превью-сборке (`VITE_PREVIEW=1`, уже выставлен в Cloudflare) вход пропускается (`bootstrapSession` → `enterPreviewSession`), но экраны висят на «Загрузка…», потому что все GraphQL-запросы уходят в никуда.

Задача: сделать так, чтобы **в превью-сборке приложение работало полностью на синтетических данных прямо в браузере — без сервера, без сети, без расходов**. Это дизайн-демо на нашем новом UI (как старый прототип, только на AIR). Многопользовательский бэкенд — отдельная будущая задача, СЕЙЧАС НЕ ТРОГАЕМ.

## Незыблемые правила
- **Только фронт.** `frontend/src/**`. Backend, SDL, docs/** не трогать.
- **Приватность/ноль egress.** Демо-слой — чисто клиентский. В превью-режиме **не должно быть ни одного сетевого запроса к `/graphql/`** (проверяется в DevTools → Network). Мутация `ReportAttention` в превью — no-op (никакая биометрия и никакие данные никуда не уходят). Это соответствует инварианту приватности проекта.
- **Гейты не ронять.** База: backend 89 pytest (не трогаем), frontend 115 vitest. После работы vitest зелёный; добавь точечные тесты на демо-линк. `tsc -b && vite build` зелёный. `eslint` без ошибок. **Никакого `any`** — фикстуры типизировать сгенерированными типами (`@/entities/graphql/generated`), формы операций брать из `*.graphql` как источник правды.
- **Обычный режим без изменений.** Всё за флагом `import.meta.env.VITE_PREVIEW === '1'`. Без флага (dev, тесты, будущий прод) поведение ровно как сейчас: реальный Apollo-чейн, реальный вход.

## Что построить

### 1. Модуль `frontend/src/shared/demo/`
- `demoData.ts` — типизированный синтетический датасет по ролям (student/teacher/parent/admin). Реалистичные русские данные, согласованные с дизайн-атласом (`docs/design-previews/atlas/`): имена, курсы (математика/физика/…), разделы/уроки, расписание (сегодня/неделя), домашние задания и статусы, группы/ученики для админа, заявки. Числа правдоподобные.
- `resolveDemoOperation.ts` — по `operation.operationName` (+ переменным, где нужно) отдаёт объект данных нужной формы. Для мутаций — меняет in-memory стор и возвращает успех.
- `demoLink.ts` — `ApolloLink`, который возвращает `Observable`, резолвящий `{ data }` из `resolveDemoOperation`, **без обращения к сети**. Для подписки `AttentionUpdates` — эмитит синтетические агрегаты по интервалу (для live-вида учителя) либо пустой поток.
- `demoRole.ts` — роль из query-параметра `?role=student|teacher|parent|admin` (дефолт `teacher`); хелпер + (опционально) маленький плавающий переключатель ролей, видимый ТОЛЬКО в превью.

### 2. Ключевая точка входа — `query Me`
В превью `Me` возвращает синтетического пользователя с ролью из `demoRole`. Именно это определяет, какой кабинет рисуется. Смена `?role=` → другой кабинет + соответствующие данные. Это линчпин — без него всё висит.

### 3. Полный охват операций (источник — `*.graphql` + generated)
**Queries:** `Me`, `MyCourses`, `MySchedule`, `MySubmissions`, `Catalog`, `CourseDetail`, `LessonHomework`, `HomeworkSubmissions`, `AdminInstitution`, `InstitutionGroups`, `InstitutionMembers`, `SessionRoom`, `SessionAttendees`, `SessionAttention`.
**Mutations (вернуть правдоподобный успех + оптимистично обновить in-memory):** `SubmitHomework`, `GradeSubmission`, `Enroll`/`Unenroll`, `CreateCourse`/`UpdateCourse`/`PublishCourse`, `Create/Update/Delete Section/Lesson`, `Reorder*`, `Add/DeleteMaterial`, `CreateHomework`/`PublishHomework`/`DeleteHomework`, `ScheduleSession`/`StartSession`/`EndSession`/`JoinSession`, админские (`CreateGroup`, `AssignTeacher`, `Add/RemoveStudent…`, `InviteMember`, `UpdateMembership`, `RemoveMember`, `UpdateInstitution`, `UpdateBranding`, `AddChild`), `SetAvatar`, `RequestUpload`. `Login`/`RegisterUser`/`Refresh…`/`Reset…` — экраны в превью пропущены, но обработай gracefully (успех).
**Subscription:** `AttentionUpdates` — синтетические тики агрегатов.

### 4. Wiring — `frontend/src/app/apolloClient.ts`
Если `VITE_PREVIEW==='1'` → `link = demoLink` (полностью вместо `splitLink`/сети). Иначе — как сейчас. Никаких сетевых линков в превью.

### 5. Особый случай — Live-комната
LiveKit (реальное видео) в браузере без сервера смоделировать нельзя. В превью:
- `SessionRoom`/`JoinSession` отдают демо-комнату, но **к LiveKit НЕ подключаемся** (guard по превью или пустой `VITE_LIVEKIT_URL`).
- Рисуем UI-оболочку комнаты с плейсхолдер-тайлами участников (аватары-инициалы) + синтетические параметры внимания на тайлах (только учителю, по нашим правилам v3), классовый средний. Индикатор приватности «на устройстве» — на месте.
- Ученик своих метрик не видит (как в v3).

## Приёмка (обязательно приложить к отчёту)
1. `?role=` × каждый кабинет (student/teacher/parent/admin) — скриншоты наполненных экранов: дашборд, курсы (каталог+деталь), расписание, домашки (список+сдача/очередь+проверка), комната. Пусто/skeleton/ошибка не должны залипать.
2. DevTools → Network в превью: **ноль запросов к `/graphql/`** (доказательство, что ничего не уходит с устройства) — скрин.
3. Консоль без ошибок.
4. Гейты: `npm test` (vitest) число; `npm run build` (tsc+vite) зелёный; `eslint` чисто.
5. Обычный режим не сломан: без `VITE_PREVIEW` приложение по-прежнему требует вход и ходит в реальный API (быстрый прогон/тест).
