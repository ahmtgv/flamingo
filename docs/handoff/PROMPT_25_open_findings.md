## 0. ЗАКОН ЭТОЙ ФАЗЫ · НЕ НАВРЕДИ

Владелец, 17.08, дословно: **«Перепроверяй что сделал! Правило трёх: новый код не должен
ломать то, что уже прекрасно работает! Перепроверяй, чтобы не было конфликтов нового
со старым! Не навреди!»**

Это не пожелание, а рамка. Основание — наша же история: **семь регрессий из десяти** родились
не из плохого кода, а из правильной правки, открывшей состояние, которого раньше не бывало.

### 0.1 Правило трёх — выполнять буквально

Для **каждой** правки, до коммита:

1. **Что я меняю** — какое поведение становится другим.
2. **Какое состояние теперь стало возможным**, чего раньше не бывало никогда. Найти **весь**
   код, который это состояние читает, и проверить каждое место. Не «подумать» — найти поиском
   и перечислить в отчёте.
3. **Что могло сломаться рядом** — сквозной прогон целиком, а не тот сценарий, который чинил.

⚠️ **Работающее не трогать.** Мастер проходит до кабинета, подпись и нотаризация в порядке,
сквозной прогон зелёный, пятнадцать проверок. Это фундамент; любая правка, задевшая его,
откатывается, а не «дочинивается на ходу».

### 0.2 После каждого залпа — полный прогон

```
npm run e2e        # 15/15 — мастер до кабинета, 7 маршрутов, axe
pytest             # 630
vitest             # 534
```

Число упало — **остановиться и разобраться**, а не идти дальше. Красный прогон после правки
важнее любой следующей задачи.

### 0.3 Проверять себя, а не полагаться на память
Каждое «сделано» в отчёте — команда и её вывод. Каждый новый тест **проверен падением**
на том дефекте, ради которого написан. Тавтологии искать отдельно: тест, берущий данные
из того же источника, что и проверяемый код, — уже трижды подводил.

## 1. 🔴 ЗАЛП 1 · ТЕСТОВЫЙ КОНТУР — ПЕРВЫМ ДЕЛОМ

Сейчас сквозной прогон ходит по **боевому** серверу и заводит там учётку при каждом запуске.
Их больше десяти, `purge_test_accounts` упирается в собственный предел десяти записей.
Это не гигиена, а риск: ночной прогон пишет в базу, где лежат живые данные.

**Сделать:**

1. Поднять бэкенд локально из `infra/` (postgres + redis + api) — отдельная база, отдельный порт.
2. Направить `e2e` туда переменной окружения. Боевой адрес остаётся значением по умолчанию
   для ручных проверок — **не ломать существующий способ**.
3. Прогон сам поднимает контур, накатывает миграции, заводит нужные учётки и **сносит их
   за собой**.
4. Поднять предел `purge_test_accounts` до сотни или сделать параметром: команда, которая
   отказывается убирать накопленное, бесполезна.

⚠️ **Не выключать проверку боевого совсем.** Один сценарий — «связывание против боевого API» —
остаётся, иначе мы перестанем ловить дефекты вроде CORS, которые живут только там.

**⛳ Ворота залпа 1:** `npm run e2e` проходит **не касаясь боевой базы**, и это доказано —
в боевой после прогона ни одной новой учётки.

## 2. 🔴 ЗАЛП 2 · ЗЕРКАЛО ГРУППОВЫХ УЧЕНИКОВ

Находка ночного аудита: **ученики из групп не зеркалятся вовсе.**

Это прямое нарушение решения владельца §20.5: **учёба ученика принадлежит ему навсегда,
доступна с любого устройства и переживает уход преподавателя.** Сейчас для группового
ученика она существует только на машине преподавателя — то есть обещание родителям неверно.

**Сделать:**

1. Разобраться, **почему** зеркалятся не все: где проходит граница «индивидуальный ученик /
   групповой», кто решает, что зеркалить.
2. Зеркалить **всех** учеников занятия, независимо от того, пришли они поимённо или группой.
3. Состав зеркала — по §20.5.1: дневник · работы со всеми попытками и файлами · саммари
   с чатом внутри · доски · выданные материалы **содержимым** · чаты.
4. **Зеркало работает только на запись** — вторая половина той же находки. Ученик должен
   уметь **прочитать** своё: с любого устройства, при выключенной машине преподавателя.
5. Тест поведением: групповой ученик открывает своё, когда машина преподавателя выключена.

⚠️ Правило трёх здесь особенно: зеркало пишут несколько мест, и добавление групп
не должно удвоить записи для тех, кто зеркалится уже сейчас.

## 3. 🔴 ЗАЛП 3 · ОСТАЛЬНЫЕ ОТКРЫТЫЕ НАХОДКИ

Все из ночного отчёта, ни одна не тронута.

### 3.1 Роль при связывании не проверяется
**Ученик может связать преподавательское приложение.** Связывание обязано отказать всем,
кроме преподавателя, и сказать словами, почему. Тест на отказ для каждой роли.

### 3.2 `advanceDeviceSetup` не вызывается
Сервер не видит шагов 2 и 4: счётчик двигают не все шаги. Отсюда рассинхрон «что машина
прошла на самом деле» — тот же, из-за которого мастер уже вставал.

### 3.3 `logout` не вызывается — токен жив две недели после «выхода»
Кнопка выхода чистит состояние в браузере и **не говорит серверу ничего**. Токен остаётся
годным. Для украденного ноутбука и для чужого компьютера это дыра.

### 3.4 `/local-files/…` не обслуживается ничем
Адрес есть, обработчика нет. Понять, кто на него ссылается: либо поднять обработчик,
либо убрать ссылки. Молчащий адрес — тот же молчащий отказ.

### 3.5 `sessionStatusChanged` — в CLAUDE.md значится работающей, резолвера нет
Либо построить, либо привести документ в согласие с кодом. Решить и записать.

### 3.6 49 осиротевших операций под храповиком
Сторож их считает. Пройти список: что задел на будущее, что забытая проводка вроде
`hostHeartbeat`. Забытую проводку — соединить, храповик опустить.

- **Время урока.** Занятие в полночь, занятие на стыке перехода на зимнее время, занятие,

- **Пустой продукт.** Новый преподаватель без курсов, ученик без занятий, группа без учеников:
