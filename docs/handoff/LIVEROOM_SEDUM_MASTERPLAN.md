**Приоритет:** максимальный. Это главный UX-фронт проекта: живой урок и SEduM — то, ради чего платформа существует.

Этот документ = (1) UX-спецификация трёх задач владельца, (2) технические инварианты, которые нельзя нарушить, (3) слайсы с критериями приёмки, (4) рабочий промпт для исполнения каждого слайса. Обновлять по мере выполнения.

## 0. Метод и жёсткие рамки

- **Design-first:** каждый слайс начинается с текстового вайрфрейма/спеки в стиле «Flamingo Air» (`docs/Flamingo_Redesign_Prompt_v2.md`), затем код.
- **Гейты зелёные на каждый коммит:** backend pytest + ruff/black; frontend build + lint + vitest. Один concern — один коммит.
- **Среда ИИ не имеет камеры/второго экрана** → всё медиа-поведение дополнительно проверяется **owner real-run протоколом** (в каждом слайсе указано, что именно). Не считать слайс DONE без протокола.
- **Классы регрессий, которые уже ловили (НЕ повторять):**
  - `7686a9c`: любой ремаунт локального `<video>` теряет `srcObject`, а размонтирование комнаты останавливает shared-трек и убивает CMF. → Смена лейаута ТОЛЬКО через data-атрибуты/CSS на одном стабильном контейнере `.tiles`; стабильные React-ключи; никаких условных ранних `return`, размонтирующих комнату.
  - `c9334d3`: reconnect-churn — не трогать логику connect/disconnect без нужды.
  - Camera toggle = `track.enabled=false`, никогда `stop()`.
- **Privacy-инвариант АБСОЛЮТЕН** (CLAUDE.md §2.1/§7): сырые кадры/landmarks не покидают устройство; эгресс — только 8 агрегатных скаляров `reportAttention`; в БД — только `avg_attention`. ВСЯ диагностика SEduM (задача 3) — on-device; отладочные данные НЕ отправляются никуда и не персистятся на сервере.
- **SDL — только hand-add** с diff'ом живой схемы; никакого `export_schema`.

## 1. ЗАДАЧА 1 — Экран учителя: фокус на ученике

### UX-спецификация (Air)

- **Базовое состояние:** ученики — равные тайлы в адаптивной сетке (сейчас ≤5; сетка проектируется масштабируемой до N, см. F4). Поверх каждого тайла — имя + мини-индикатор внимания (существующая грамматика).
- **Клик по тайлу → «фокус»:** выбранный ученик плавно (токенные длительности) занимает центральную сцену; остальные уменьшаются в бок/низ-филмстрип, но ОСТАЮТСЯ на экране и продолжают жить (видео + внимание). Повторный клик / Esc / клик по другому тайлу — возврат/смена фокуса. Механика зеркалит уже существующий screen-share-лейаут (`data-screen`) — реализация тем же паттерном: `data-focus="<participantId>"` на стабильном `.tiles`.
- **Режим (a) — на весь экран:** кнопка на фокус-сцене → Fullscreen API на контейнере сцены (не на `<video>` — оверлеи имени/внимания должны остаться). Esc/системный выход возвращают в (b)-состояние без ремаунта.
- **Режим (b) — максимально, но с навигацией кабинета:** фокус-сцена растягивается на всю рабочую область приложения; glass-topbar и контролы комнаты остаются видимы. Это дефолт фокуса.
- **Режим (c) — второй экран (планшет), на весь экран:** отдельный **projector-view** — маршрут `/sessions/:id/room?view=projector[&focus=<studentId>]`: только видео+имена (опционально одно фокус-видео), без контролов, тёмная канва, авто-fullscreen-подсказка. Учитель открывает URL на планшете под своим логином. Синхронизация выбранного фокуса между окнами — фаза 2 (см. F3): начинаем со статического `?focus=`, затем realtime-канал.
- **Много учеников:** сетка авто-уплотняется (auto-fill, минимальный тайл ~160px); в фокусе филмстрип скроллится; позиции СТАБИЛЬНЫ (insertion order, никакой пересортировки по данным — правило орбов).
- **A11y:** тайл — настоящая `<button>`-обёртка (`aria-pressed`/`aria-label` «Развернуть видео: Имя»), Esc закрывает фокус, фокус клавиатуры управляем, reduced-motion отключает transition размеров.

### Технические заметки (по реальному коду)

- `useLiveKitRoom` уже отдаёт участников и треки; фокус — чисто presentation-state (`useState<participantId|null>` в `TeacherRoom`/`VideoRoom`), НИКАКИХ изменений hook'а для F1–F2.
- **Projector (F3) требует backend-решения:** сейчас `room_token` минтит полноценный VideoGrant, а `roomFull`-гард отключает 6-го участника. Projector-подключение должно быть **subscriber-only + hidden** (LiveKit VideoGrant: `canPublish=false`, `hidden=true`) и НЕ считаться в ≤5. → сервисный параметр `room_token_for(user, session, view="projector")` + SDL hand-add аргумента к `roomToken`-полю ИЛИ отдельная query (решить при исполнении; diff живой схемы обязателен). Projector-view не запускает CMF и ничего не публикует.
- Fullscreen API: `requestFullscreen` на элементе сцены; обработать `fullscreenchange` (выход системной кнопкой); Safari/iPad — `webkit`-префиксы (планшет!).

### Слайсы и приёмка

- **F1 — фокус в сетке (клик/Esc/смена, филмстрип, анимация, a11y).** Приёмка: vitest на состояние/aria + отсутствие ремаунтов (тест по ключам/instance), запись CMF продолжается при смене лейаута (тест как в 7686a9c-регрессии); owner-run: 2 окна, фокус туда-обратно — камера не чернеет, внимание течёт.
- **F2 — fullscreen (a) + max-with-nav (b).** Приёмка: vitest на состояния; owner-run: вход/выход fullscreen мышью и Esc, iPad Safari — поведение webkit.
- **F3 — projector-view (c):** backend hidden-token + маршрут + минимальный UI; статический `?focus=`. Приёмка: pytest на grant-флаги (публикация запрещена, hidden), projector не влияет на roomFull; owner-run: планшет реально показывает эфир fullscreen.
- **F3.1 (после F3) — live-синхронизация фокуса** учитель→projector (существующая graphql-ws инфра, teacher-only канал; payload = studentId, НИКАКИХ метрик сверх уже идущих агрегатов).
- **F4 — масштаб N>5 (дизайн сейчас, включение позже):** лейаут и виртуализация проектируются на N, но runtime-cap остаётся ≤5 до решения по hard cap (серверный `max_participants` — отдельный бэклог-пункт). Открытый вопрос владельцу: целевой размер класса (§6).

## 2. ЗАДАЧА 2 — Экран ученика (продумать)

### Предлагаемая UX-модель (Air, «спокойный класс»)

Принцип: ученик смотрит НА УЧИТЕЛЯ, а не на себя; себя — маленьким; метрики — тихо, поддержкой, не оценкой.

- **Дефолт «Урок»:** учитель — большая центральная сцена; свой тайл — маленький в углу (с AttentionStrip поверх, как сейчас); контролы снизу; privacy-индикатор всегда.
- **Screen share учителя** автоматически становится сценой, учитель — в мини-тайл (уже работает — сохранить).
- **Одноклассники:** по умолчанию СКРЫТЫ или крошечный ряд аватаров без видео (меньше отвлечения + приватность детей) — **вопрос владельцу (§6): показывать ли видео одноклассников ученику вообще.**
- **Свой фокус:** клик по своему тайлу — разворот своей полоски внимания (существующий манёвр Strip), НЕ фуллскрин себя.
- **Слайс S1:** привести студенческий лейаут к этой модели (teacher-primary вместо равной сетки) + Air-композиция контролов. Приёмка: vitest; owner-run 2 окна.

## 3. ЗАДАЧА 3 — SEduM 2.0: довести модуль до отличной работы

Сейчас: пороги в `cmfConfig.ts` — первые прикидки; калибровка не вшита (скоринг без базовой линии); жалоба владельца — «работа неудовлетворительная». Лечим системно, а не подкруткой.

- **Фаза D0 — ДИАГНОСТИКА (первая, обязательная).** Нельзя чинить, не измерив.
  - Dev-only **debug-HUD** в комнате (флаг `?cmfDebug=1`, только DEV-сборка): live-график сырого скора vs EMA, все суб-метрики, FPS инференса, время кадра, дропы, confidence FaceLandmarker. **Всё on-device, ноль эгресса** — HUD не меняет `reportAttention`.
  - **Протокол воспроизведения с владельцем** (15 мин, реальная камера): сценарии — смотрю в экран / отвернулся / пишу в тетради (взгляд вниз — НЕ должен считаться невниманием!) / встал / плохой свет / очки / далеко-близко к камере. Фиксируем: где скор врёт, где скачет, где лагает.
  - Выход: список дефектов с приоритетами → уточнение фаз ниже.
- **Фаза C1 — КАЛИБРОВКА «база тест» (главный структурный дефект).**
  - Worker получает `mode:'calibration'`, эмитящий per-stage `AttentionSignals` (машина `seedum/calibration.ts` уже готова и оттестирована); 3-шаговый UI-мастер при онбординге/из профиля; baseline → UBP (IndexedDB); скоринг нормализуется относительно ЛИЧНОЙ базовой линии (у каждого своя посадка/глаза/камера — это устраняет класс «у всех разный ноль»).
  - Опционально следом: `backupUbp`-wiring (шифрование уже написано).
- **Фаза Q2 — КАЧЕСТВО СКОРИНГА.**
  - Гистерезис/асимметричное EMA (быстро вверх, медленно вниз — не дёргается), окно уверенности (низкий confidence → «нет данных», не ложный ноль), «взгляд вниз на тетрадь» как отдельное состояние (head-pitch-вниз + стабильность ≠ невнимание), обработка морганий/очков/освещения по итогам D0. Все константы — ТОЛЬКО в `cmfConfig.ts`; модель задокументировать в `docs/` (что значит каждая компонента).
- **Фаза P3 — ПРОИЗВОДИТЕЛЬНОСТЬ.**
  - Профилировка воркера; адаптивный frame-rate (снижать частоту инференса при стабильном состоянии, повышать при изменениях); backpressure (не копить кадры); замер CPU/батареи до/после; цель — комната 45 минут без нагрева/дропов на среднем ноутбуке.
- **Фаза T4 — ТЮНИНГ ПОРОГОВ С ВЛАДЕЛЬЦЕМ.** Повторить протокол D0 на калиброванной, ускоренной версии; крутить `cmfConfig` до «глазами верю цифре»; зафиксировать значения как «tuned v1» (снять пометку PROVISIONAL).
- **Приёмка модуля целиком:** на протоколе сценариев скор соответствует поведению (согласие владельца), нет скачков >N пунктов между соседними бакетами без смены поведения, «нет данных» никогда не показывается как 0 или как «в кадре», FPS/CPU в бюджете, privacy-тесты зелёные и **неизменные** (`test_attention_input_is_aggregate_only` — 8 скаляров, как было).
