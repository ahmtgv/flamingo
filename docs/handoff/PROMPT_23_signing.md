## 2. ШАГ 1 · ПОДПИСЬ

### 2.1 Прописать сертификат
`desktop/src-tauri/tauri.conf.json` → `bundle.macOS.signingIdentity` = имя из §0.

⚠️ **Не хардкодить, если можно через переменную окружения** (`APPLE_SIGNING_IDENTITY`).
Имя не секрет, но машина сборки может смениться, и конфигурация не должна это ломать.

### 2.2 🔴 Hardened runtime и entitlements — здесь легко сломать камеру

Нотаризация требует **hardened runtime**. Под ним по умолчанию **запрещено** то, что работало
у неподписанного приложения. Для нашего случая почти наверняка нужны:

| Entitlement | Зачем |
|---|---|
| `com.apple.security.cs.allow-jit` | JavaScriptCore внутри WKWebView |
| `com.apple.security.device.camera` | шаг 4 мастера и урок |
| `com.apple.security.device.audio-input` | микрофон |
| `com.apple.security.network.client` | запросы к `api.flamingo.plus` |

⚠️ **Список — гипотеза, а не истина.** Проверять поведением: собрать, установить, пройти
шаг 4 и убедиться, что превью и уровень звука работают. Если что-то отвалилось — назвать
дословно, что сказала система, и добавить недостающее.

⚠️ **Отдельно проверить связку ключей под hardened runtime.** Ключ машины должен писаться
и читаться, как в §2.5 промпта 21: **запись в одном процессе, чтение в другом**. Проверка
внутри одного процесса ничего не доказывает — на этом уже обжигались (Р-7).

### 2.3 Не ломать установщик
`desktop/install.sh` уже умеет: если на приложении **настоящая** подпись — не трогать её
ad-hoc'ом (строки 92–103). Проверить, что после подписи он ведёт себя правильно, и убрать
ad-hoc ветку, когда настоящая подпись станет обязательной.

## 3. ШАГ 2 · НОТАРИЗАЦИЯ

### 3.1 Что нужно от владельца — уже согласовано
Идём **не** через ключ App Store Connect (`.p8`), а через пароль приложения: шагов меньше,
и владельцу не надо возиться с ключами API.

Пароль приложения создаётся на [appleid.apple.com](https://appleid.apple.com) → Вход
и безопасность → Пароли для приложений. Кладётся **в связку ключей**, не в файл:

```bash
xcrun notarytool store-credentials "flamingo-notary" \
  --apple-id "<почта владельца>" \
  --team-id 9MSP6HD8P6 \
  --password "<пароль приложения>"
```

Владелец выполняет это у себя **сам**, один раз. Дальше в сборке используется только имя
профиля `flamingo-notary` — оно не секрет.

### 3.2 Отправить и приклеить
Нотаризовать `.dmg`, дождаться результата, затем `stapler staple` **и на `.app`, и на образ** —
иначе на машине без интернета Gatekeeper не сможет проверить.

При отказе — забрать журнал (`notarytool log`) и привести причину дословно.

**Не должно быть** ни `adhoc`, ни `linker-signed`, ни `Info.plist=not bound`.

## 5. ШАГ 4 · 🔴 ПРИЁМКА Р-8 — ИМЕННО ТАК, ПО ПОРЯДКУ

Запись Р-8 в `REGRESSION_LOG.md` помечена **закрытой подписью**, а отчёт того же дня говорит:
«окно при первом запуске остаётся». Одно из двух неправда.

**Переоткрыть Р-8** и закрывать только результатом этого прогона:

```
собрать подписанную версию
→ установить
→ спарить с нуля
→ на запрос связки нажать «Разрешать всегда»
→ пересобрать БЕЗ ЕДИНОЙ ПРАВКИ исходников
→ перезапустить
→ окно появилось или нет
```

**Появилось** — Р-8 открыта, разбираться дальше. **Не появилось** — закрыть и записать,
что закрыла именно подпись, а не устойчивый ad-hoc идентификатор.

⚠️ Прежнее объяснение («закрепил `-i`») правдоподобно и **не доказано**: у ad-hoc подписи
требование строится на `cdhash`, а он меняется с каждой сборкой независимо от идентификатора.
Гипотеза могла быть верной и могла не быть — прогон решит.

## 6-бис. ОТВЕТЫ НА ЧЕТЫРЕ ВОПРОСА ИЗ ОТЧЁТА 16.08

**1. Developer ID — выпущен, вот он.** Имя и Team ID в §0. Отчёт писался раньше, чем владелец
его создал, — поэтому там и сказано «сертификата в аккаунте нет». Теперь есть.

**2. Профиль нотаризации** — идём через пароль приложения, а не ключ API (§3.1). Владелец
создаёт профиль у себя одной командой; в чат ничего не присылает.

**3. Тестовые учётки — сделать management-команду, а не просить доступ к базе.**
`test-teacher-*@flamingo-test.invalid` удаляются командой Django, которую владелец запускает
на сервере сам:

```bash
docker compose -f infra/prod/docker-compose.prod.yml --env-file .env.production \
  exec api python manage.py purge_test_accounts --confirm
```

Требования к команде:
- удаляет **только** почты по маске `*@flamingo-test.invalid` — маска зашита в код,
  параметром не передаётся;
- без `--confirm` показывает список и **ничего не делает**;
- печатает, что именно удалено: учётки, машины, сессии, согласия;
- отказывается работать, если под маску попало больше десяти записей — защита от опечатки.

⚠️ **Мутации удаления пользователя в схеме не заводить.** Разовая уборка тестового мусора —
не повод открывать в API дверь, которой там быть не должно (и §20.5: данные ученика
не удаляются). Команда живёт в `manage.py`, а не в GraphQL.

**4. Порядок — сначала подпись до конца, потом доска.** Она уже разблокирована и стоит
недорого, а без неё каждая пересборка этапа 2 будет выбивать владельцу окно с паролём.
Доска — сразу следом.
