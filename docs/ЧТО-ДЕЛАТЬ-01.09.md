| `Permission denied (publickey)` | ключа нет, идём в 3б |

**3а. Ключ есть:**

```

```

🔴 **Именно `-b v1`, а не просто clone.** На GitHub ветка `main` СТАРАЯ: мы
пушим `main:v1`, то есть боевая ветка — `v1`. Обычный `git clone` возьмёт

**3б. Ключа нет — завести ключ развёртывания:**

```
ssh-keygen -t ed25519 -C "flamingo-server" -f /root/.ssh/id_ed25519 -N ""
cat /root/.ssh/id_ed25519.pub
```

Вывод последней команды скопировать в GitHub → репозиторий `flamingo` →
Settings → **Deploy keys** → Add deploy key → вставить, галку «Allow write
access» **не** ставить: серверу писать в репозиторий незачем.

Проверить, что ключ принят:

```

```

Ждём `Hi ahmtgv/flamingo! You've successfully authenticated…`.

## Шаг 6. Настройки

```
nano /opt/flamingo-v2/backend/.env
```

Целиком:

```
SECRET_KEY=<сюда вывод команды ниже>
DEBUG=0
ALLOWED_HOSTS=api.flamingo.plus,127.0.0.1,localhost
CORS_ALLOWED_ORIGINS=https://flamingo.plus
SESSION_COOKIE_DOMAIN=.flamingo.plus
DB_PATH=/var/lib/flamingo/flamingo.sqlite3
MEDIA_ROOT=/var/lib/flamingo/materials
MATERIAL_MAX_MB=64
MATERIALS_MAX_GB=5
LIVEKIT_URL=
LIVEKIT_API_KEY=
LIVEKIT_API_SECRET=
```

🔴 **`LIVEKIT_*` остаются пустыми, и это правильно.** Токен для эфира фронт
берёт у функции Cloudflare Pages из своего же выката, а не у этого сервера
(`frontend/src/lib/api.ts`: на боевом адрес не берётся из окружения вовсе).
Пустые ключи здесь комнату не ломают.

Ключ взять отсюда:

```
python3 -c "import secrets; print(secrets.token_urlsafe(64))"
```

🔴 `SESSION_COOKIE_DOMAIN` — ровно `.flamingo.plus`, **с точкой впереди**.
Без точки куку увидит только `api`, и человека будет выкидывать после каждого
перехода на сайт.

🔴 `SECRET_KEY` подписывает куки входа. Мне его показывать не надо.

Права на файл:

```
chown www-data:www-data /opt/flamingo-v2/backend/.env
chmod 600 /opt/flamingo-v2/backend/.env
```

🔴 **Сначала `chown`, потом `chmod`.** Один `chmod 600` от root означает
«читать может только root» — а служба работает под `www-data` и не смогла бы
прочитать собственные настройки. Упало бы при запуске, и по сообщению это
не угадывается.

🔴 `127.0.0.1` и `localhost` в `ALLOWED_HOSTS` нужны для проверки с самого
сервера: без них Django отвечает `Bad Request (400)` на свой же `curl`,
и выглядит это как «ничего не работает».

## Шаг 10. Маршрут снаружи — через Caddy

Разведка показала: 443 держит **Caddy** (`flamingo-prod-caddy-1`, `caddy:2-alpine`),
`Caddyfile` лежит на хосте в `/opt/flamingo/infra/prod/Caddyfile` и примонтирован
в контейнер. Шлюз докер-сети `flamingo-prod_default` — **172.18.0.1**.

Сейчас `{$API_DOMAIN}` (это `api.flamingo.plus`) уходит на **старый** контейнер
`api:8000` из прошлой итерации. Его-то «Not Found» вы и видели. Переводим адрес
на наш бэкенд.

### 10а. Служба должна слушать шлюз, а не только петлю

🔴 Вот главная тонкость. `--bind 127.0.0.1:8000` — это петля САМОГО ХОСТА.
Из контейнера Caddy туда не достучаться: его пакеты приходят на адрес шлюза,
а не на loopback. Нужен второй адрес.

```
sed -i 's|--bind 127.0.0.1:8000|--bind 127.0.0.1:8000 --bind 172.18.0.1:8000|' \
  /etc/systemd/system/flamingo.service
sed -i 's|^After=network.target|After=network.target docker.service|' \
  /etc/systemd/system/flamingo.service
systemctl daemon-reload
systemctl restart flamingo
ss -ltnp | grep 8000
```

Ждём ДВЕ строки: `127.0.0.1:8000` и `172.18.0.1:8000`.

`After=docker.service` — чтобы при перезагрузке сервера служба не поднялась
раньше, чем docker создаст сеть: адреса 172.18.0.1 тогда ещё не существует
и bind падает.

⚠️ Адрес шлюза привязан к сети `flamingo-prod_default`. Если её когда-нибудь
пересоздадут (`docker compose down` с удалением сети), номер может смениться —
и связь порвётся. Проверяется той же командой из разведки.

🔴 Почему именно шлюз, а не `0.0.0.0`: `0.0.0.0` открыл бы порт 8000 всему
интернету на `82.147.71.204:8000`, в обход Caddy и без TLS. Адрес шлюза —
внутренний интерфейс хоста, снаружи он не маршрутизируется.

### 10б. Перевести адрес в Caddy

```
cd /opt/flamingo/infra/prod
cp Caddyfile Caddyfile.до-flamingo-v2
sed -i 's|reverse_proxy api:8000|reverse_proxy 172.18.0.1:8000|' Caddyfile
grep -n reverse_proxy Caddyfile
```

Ждём: первый `reverse_proxy 172.18.0.1:8000` (наш), второй `minio:9000`
(файлы прошлой итерации, его не трогаем).

Копия рядом — откат в одну команду: `cp Caddyfile.до-flamingo-v2 Caddyfile`.

### 10в. Перечитать настройку

```
docker exec flamingo-prod-caddy-1 caddy reload --config /etc/caddy/Caddyfile
```

Не вышло — перезапустить контейнер:

```
docker compose restart caddy
```

🔴 Сертификат Caddy выпустит сам: домен уже указывает сюда, запись серая.
Возиться с Let's Encrypt руками не надо — ровно об этом написано в шапке
их же `Caddyfile`.

Старый контейнер `flamingo-prod-api-1` при этом остаётся жить, просто снаружи
его больше не спрашивают. Гасить прошлую итерацию — отдельное решение на потом.
